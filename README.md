<h1 align="center"> Cloud Storage </h1>

Многопользовательское файловое облако на Spring Boot. Пользователи могут регистрироваться, авторизовываться, создавать директории, загружать, скачивать, перемещать, переименовывать, удалять и искать файлы и папки.

Проект реализован на **Java 21** с использованием **Spring Boot**, **PostgreSQL**, **Redis**, **MinIO**, **Liquibase**, **Docker Compose**, **Maven**, **Testcontainers** и **OpenAPI / Swagger UI**, **Logging**.

---

## Возможности

* регистрация, авторизация и выход из аккаунта;
* хранение пользовательских сессий в Redis;
* создание и просмотр директорий;
* загрузка одного или нескольких файлов;
* получение информации о файлах и папках;
* скачивание файла в исходном виде;
* скачивание директории как ZIP-архива;
* перемещение и переименование файлов и директорий;
* удаление файлов и директорий;
* поиск ресурсов по имени;
* изоляция файлов разных пользователей.

## Быстрый старт (локально)

### Требования

Перед запуском должны быть установлены:

* JDK 21
* Maven
* Docker / Docker Compose

### 1. Настроить окружение

Скопируйте:

```text
.env.example
```

в:

```text
.env
```

и укажите локальные значения:

```dotenv
POSTGRES_USER=cloud_user
POSTGRES_PASSWORD=cloud_password
POSTGRES_DB=cloud_storage_db

MINIO_USER=minio_admin
MINIO_PASSWORD=minio_password
```

Файл `.env` не должен попадать в Git.

### 2. Запустить инфраструктуру

```bash
docker compose up -d
```

Docker Compose поднимает PostgreSQL, Redis и MinIO.

### 3. Настроить Spring Boot

В IntelliJ IDEA откройте:

```text
Run → Edit Configurations → CloudStorageApplication
```

и добавьте переменные окружения:

```text
POSTGRES_DB=cloud_storage_db;POSTGRES_USER=cloud_user;POSTGRES_PASSWORD=cloud_password;MINIO_USER=minio_admin;MINIO_PASSWORD=minio_password
```

Значения должны совпадать со значениями в `.env`.

После этого запустите `CloudStorageApplication`.

## API

Все ручки API находятся под префиксом:

```text
/api
```

### Пользователь

| Метод | URL | Назначение |
|---|---|---|
| POST | `/auth/sign-up` | Регистрация |
| POST | `/auth/sign-in` | Авторизация |
| POST | `/auth/sign-out` | Выход |
| GET | `/user/me` | Получение текущего пользователя |

### Директории

| Метод | URL | Назначение |
|---|---|---|
| POST | `/directory?path={path}` | Создание директории |
| GET | `/directory?path={path}` | Получение содержимого директории |

### Ресурсы

| Метод | URL | Назначение |
|---|---|---|
| POST | `/resource?path={path}` | Загрузка файлов |
| GET | `/resource?path={path}` | Получение информации о ресурсе |
| DELETE | `/resource?path={path}` | Удаление ресурса |
| POST | `/resource/move?from={from}&to={to}` | Перемещение / переименование |
| GET | `/resource/download?path={path}` | Скачивание файла или директории |
| GET | `/resource/search?query={query}` | Поиск ресурсов |

Ошибки API возвращаются в едином формате:

```json
{
  "message": "error message"
}
```

## Ключевые решения

### Хранение файлов

Файлы хранятся в MinIO.

Для каждого пользователя используется отдельный логический root:

```text
user-{id}-files/
```

Директории представлены zero-byte marker objects с `/` в конце имени, что позволяет сохранять в объектном хранилище в том числе пустые директории.
Имена файлов на `/` не оканчиваются.

### Сессии

Авторизация основана на HTTP-сессиях. Сессии хранятся в Redis через Spring Session.

### База данных

PostgreSQL используется для хранения пользователей. Изменения схемы выполняются через Liquibase (см. changelog / changesets).

### DTO

Для resource API используется общий `ResourceResponse`.

Дополнительное дробление DTO и отдельный слой MapStruct не вводились: преобразования небольшие, и для текущего объёма проекта это не даёт практической пользы.

### Обработка исключений

Ошибки обрабатываются централизованно через GlobalExceptionHandler.

Исключения разделены на несколько групп:

- известные application exceptions — ошибки, предусмотренные API и ТЗ (400, 401, 404, 409 и т. д.);
- общие инфраструктурные исключения — например ошибки при работе с MinIO, которые не должны протекать в сервисный и controller-слой деталями конкретной библиотеки;
- непредусмотренные исключения — остальные ошибки, в том числе необработанные RuntimeException, для которых приложение не может достоверно определить отдельный HTTP-код; они возвращаются как 500 Internal Server Error;
- исключения Spring MVC / validation — ошибки валидации request DTO, параметров запросов и другие ошибки обработки HTTP-запроса со стороны Spring.

API возвращает ошибки в едином формате:

```
{
"message": "error message"
}
```

### Logging

В проекте используется SLF4J + Logback.

Логируются основные пользовательские и storage-операции, а также ошибки приложения.

Уровни логирования разделены по смыслу:

- INFO — успешные значимые операции;
- DEBUG — диагностическая информация;
- WARN — ожидаемые ошибки запроса и известные application exceptions;
- ERROR — неожиданные ошибки приложения (500) с полным stack trace.

## Тесты

В проекте используются:

* unit-тесты сервисов;
* WebMvc-тесты контроллеров;
* интеграционные тесты с PostgreSQL, Redis и MinIO через Testcontainers;
* HTTP-сценарии для проверки API.

Интеграционные тесты также проверяют изоляцию пользовательских ресурсов.

Запуск Java-тестов:

```bash
mvn clean test
```

Запуск HTTP-тестов осуществляется из среды разработки Идея и его нужно вызывать из архива
как "выполнить все", т.к. есть зависимость тестов от их порядка.
